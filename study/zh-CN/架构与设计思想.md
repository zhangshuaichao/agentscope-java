# 架构与设计思想

本文区分“源码事实”和“设计解读”。解读帮助建立心智模型，不代表作者对每项决策的历史解释。

## 1. 先看分层，而不是先读最长的类

- **core**：Agent 契约、ReAct 循环、消息、事件、工具、中间件与状态。
- **harness**：组合工作区、记忆、技能、子智能体、沙箱等高层能力。
- **extensions**：模型供应商、存储、协议、框架与渠道适配。
- **examples**：演示如何组装应用。
- **service**：服务化入口及控制面等，不是核心推理算法本身。

源码依据：[AGENTS.md 项目边界](../../AGENTS.md)、[Harness 架构](../../docs/v2/zh/docs/harness/architecture.md)。

设计解读：把“如何推理和调用工具”与“在哪里存储、怎样接入供应商、怎样部署”分开，可以用测试替身验证核心行为，也避免核心层依赖具体供应商。

## 2. 一次调用的主线

阅读入口：[ReActAgent](../../agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java)、[AgentBase](../../agentscope-core/src/main/java/io/agentscope/core/agent/AgentBase.java)。

```text
输入消息 + RuntimeContext
  → call(...) 或 streamEvents(...)
  → buildAgentStream / 生命周期与中间件
  → 为当前调用取得正确的 AgentState
  → reasoning：准备消息、工具 schema、生成配置并调用模型
  → 解析模型输出
       ├─ 可结束的回答 → 终结消息
       └─ 工具请求 → 权限判定 → acting → 关联工具结果 → 下一轮 reasoning
  → 保存状态 / 产生结束事件 / 清理本次执行资源
```

这是正常流程的简化图，不穷举错误、取消、暂停、重试、结构化输出和恢复分支。阅读时重点搜索 `callInternal`、`buildAgentStream`、`runLifecycle`、`CallExecution`、`reasoning`、`runPostReasoningPipeline`、`acting`、`evaluatePermissions`、`dispatchToolCalls`。

源码事实：`call()` 与 `streamEvents()` 共享 `buildAgentStream`；`callInternal` 从事件流中提取终结结果。流式接口不是独立复制的一套循环。

设计解读：共享执行核心减少“流式能工作、非流式不一致”的维护风险。比较两种接口时，应检查最终消息一致性，不只检查是否出现文字。

## 3. 能力接口组合，而非把所有功能塞进 Agent

[Agent](../../agentscope-core/src/main/java/io/agentscope/core/agent/Agent.java) 组合 `CallableAgent`、`StreamableAgent`、`ObservableAgent`。其契约说明，观察消息不一定生成回复；记忆管理与结构化输出并不要求所有 Agent 以同一方式实现。

设计解读：调用方按能力使用对象。观察与回复分离，使多智能体协作不必把每一次消息广播都当成一次必须回应的请求。

## 4. 响应式 API 是执行契约，不只是返回值包装

[Model.stream](../../agentscope-core/src/main/java/io/agentscope/core/model/Model.java) 返回 `Flux<ChatResponse>`；[AgentTool.callAsync](../../agentscope-core/src/main/java/io/agentscope/core/tool/AgentTool.java) 返回 `Mono<ToolResultBlock>`。

设计解读：错误、取消、完成和增量结果都是执行的一部分。随意在事件循环里阻塞，或绕开框架启动一个没有生命周期管理的订阅，可能破坏取消、清理与状态保存。阅读操作符时问三个问题：什么时候开始执行？错误向哪里传播？取消后谁负责收尾？

## 5. 中间件不是“所有 hook 都一样”

[MiddlewareBase](../../agentscope-core/src/main/java/io/agentscope/core/middleware/MiddlewareBase.java) 区分：

- 洋葱式拦截：`onAgent`、`onReasoning`、`onActing`、`onModelCall`，通过 `next` 包装执行。
- 顺序转换：`onSystemPrompt`，逐步转换系统提示词。
- 单向通知：`onAgentStateReady`，无 `next` 委派。

[MiddlewareChain.build](../../agentscope-core/src/main/java/io/agentscope/core/middleware/MiddlewareChain.java) 从后往前包装，使列表首项位于最外层。`order()` 数值越大优先级越高；同优先级保留注册顺序。`activePoints()` 决定参与哪些拦截点，不是自动检测重写了哪些方法。

设计解读：按扩展点增加行为，避免继承或复制庞大的循环。不要把“改写了方法”误认为“此方法一定会被调用”。

## 6. 会话隔离：调用身份与可恢复状态分开

[RuntimeContext](../../agentscope-core/src/main/java/io/agentscope/core/agent/RuntimeContext.java) 含 `userId`、`sessionId`、`runId`、属性和调用级 AgentState 引用；属性不持久化。并发场景下，中间件和工具应优先使用调用上下文提供的状态。

[AgentState](../../agentscope-core/src/main/java/io/agentscope/core/state/AgentState.java) 含对话历史、摘要、当前轮次与权限／工具／任务等子状态。`getContext()` 返回防御性副本，`contextMutable()` 返回可变实时引用。

设计解读：同一个 Java 对象不天然等于一个用户会话。显式区分身份、执行与状态可以降低跨用户串话风险；防御性副本与可变引用的分离则让读者明确自己是否正在修改真实状态。

## 7. 工具调用是协议与状态机，不是反射调用就结束

[Tool](../../agentscope-core/src/main/java/io/agentscope/core/tool/Tool.java) 的注解元数据帮助工具集生成模型可理解的 schema；`AgentTool` 定义异步调用契约；`ToolUseBlock` 与 `ToolResultBlock` 承载调用和返回。

需要特别注意：

- 模型发出工具请求后仍需权限判定，不能把“模型选择了工具”当成授权。
- `externalTool` 会把调用作为暂停状态交给调用方，不执行本地工具体。
- `returnDirect` 是执行后的行为开关，不是模型可见的 schema 指令；批量工具、混合执行与恢复有明确限制。
- 工具描述和提示词属于运行时字符串。本学习版不翻译它们，以免改变模型行为。

设计解读：真实系统中的人工确认、外部执行和中断要求保留“尚未完成”的状态，不能统一压成成功或异常两类。

## 8. 能力检测优于假定所有模型行为相同

[Model](../../agentscope-core/src/main/java/io/agentscope/core/model/Model.java) 分别暴露原生结构化输出、与工具并用的支持程度、指定工具强制选择能力。默认值和回退策略并不相同。

设计解读：API 兼容不代表语义完全兼容。先检测能力，再选原生 schema、合成 `generate_response` 工具或提示提醒，比把某供应商假设写死在所有模型路径更稳健。

## 9. Harness 是组合层，不是第二套 ReAct

[HarnessAgent](../../agentscope-harness/src/main/java/io/agentscope/harness/agent/HarnessAgent.java) 与其 [middleware 目录](../../agentscope-harness/src/main/java/io/agentscope/harness/agent/middleware) 展示工程能力如何组合到核心生命周期。工作区访问应经过对应抽象；直接使用宿主机文件路径在沙箱或远程存储模式下可能访问错误的位置。

当前版本区分调用内状态、跨调用恢复与跨会话长期记忆。旧 `core.memory.Memory` 接口已带弃用标记，不能把它当作理解 v2 当前上下文管理的唯一入口。

## 用这些设计原则评审自己的智能体

- 是否把供应商差异封装在适配层，而不是散落在业务流程？
- 会话状态是否可能从共享对象字段泄漏到其他调用？
- 流式与非流式结果是否由同一执行核心产生？
- 权限确认、取消、恢复、工具结果关联是否被完整建模？
- 新功能能否用中间件、工具或扩展完成，而不复制主循环？
